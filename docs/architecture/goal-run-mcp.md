# Goal Run MCP v1

**Status:** The Windows build admits one approved run with up to five concurrent Codex sessions. Omit `codingTasks` for read-only review. Supply it for sandboxed changes in detached worktrees. The operator approves a clean local checkout, base SHA, file scopes and exact verification commands once. Each task receives up to two turns. Coding tasks stop after verification succeeds, or get a second turn if the check failed. Stop prevents further dispatch and asks Codex to interrupt known turns. An interrupted run can resume from its original deadline and exact outbox receipts. Desktop startup attempts recovery when exactly one approved run qualifies. Pause, automatic context rollover and quota scheduling remain pending.

The operator sends one goal from Codex. LazyPrompting plans bounded tasks, reads completed Codex results, verifies evidence, and sends follow-ups until the goal reaches a terminal state or needs the operator. The Windows host keeps running while the originating chat is closed. The browser remains available for manual use. Goal runs consume structured Codex App Server events without Computer Use or reading ChatGPT Web.

## Public interface

Keep the existing four public MCP tools. Register these capabilities behind `search_capabilities`, `describe_capability` and `invoke_capability`. `status` reports whether the Windows goal-run host is available. The host, rather than the short-lived MCP process, owns every run.

| Capability | Input | Result |
|---|---|---|
| `goal_run.start` | `requestId`, `objective`, `repositoryPath`, `baseRef`, `acceptance[]`, optional `codingTasks[]` and `limits` | `runId`, resolved base SHA, effective limits, state. A duplicate request ID with the same input returns the existing run. Different input returns `REQUEST_CONFLICT`. |
| `goal_run.status` | `runId` | Run state, checkpoint revision, and each task's state, latest verified evidence, and reason for waiting. |
| `goal_run.report` | `runId` | Outcome, per-task changes and verification, unresolved items, worktree paths and usage totals. Available for partial runs. |
| `goal_run.turn_receipt` | Exact `runId`, `taskId`, `turnId` | Native read-only **record correlation** for an approved run's persisted Codex turn, prompt/outbox receipt, base SHA and task scope. No final-turn host attestation, QA PASS or next-prompt authority. | 
| `goal_run.control` | `runId`, `action` of `pause`, `resume`, or `stop` | Current state. Repeating an already applied transition has no additional effect. |

Reject unknown fields, invalid IDs, noncanonical paths and oversized strings. `requestId` is a caller-generated UUID. `runId` is opaque and generated by the host. `repositoryPath` identifies one existing local checkout, and `baseRef` resolves to a commit in that checkout. `objective` and `acceptance` describe work and proof. They carry no permission to execute shell commands or publish changes. Requests for unsupported capability or state transitions fail with a stable error code. Compact results omit transcripts, credentials, environment contents and unrelated filesystem paths.

Example start arguments:

```json
{
  "requestId": "63ec48ad-a7be-4b26-8654-2847aa4f7845",
  "objective": "Fix the listed validation bugs in the test repository",
  "repositoryPath": "D:\\Work\\qa-repo",
  "baseRef": "Local",
  "acceptance": ["Fix input validation and pass the existing regression check"],
  "codingTasks": [{
    "files": ["src/validate.mjs"],
    "verify": ["C:\\Program Files\\nodejs\\node.exe", "--test", "tests/validate.test.mjs"]
  }],
  "limits": { "maxActiveTasks": 5, "maxTurnsPerTask": 2, "wallMinutes": 30 }
}
```

`codingTasks` has one entry per acceptance criterion. Paths are repository-relative and disjoint across tasks. `verify` is the exact argv displayed during approval, starting with an absolute existing Windows executable. The verification runs read-only for up to 30 seconds. A coding receipt includes changed paths, a digest of their contents and the verifier's exit code. The run leaves its worktrees available for review.

Effective ceilings are five active tasks across the host, two turns per task and 30 wall minutes per run. At the deadline the executor stops issuing new turns and requests interruption of running turns. Token accounting remains pending.

## Ownership and authorization

1. The trusted Windows host receives the MCP request through its local protected transport. Before creating worktrees or dispatching, it presents one native confirmation with the exact repo, branch and resolved SHA, acceptance criteria, permissions and limits. This is the run's initial approval. Tool arguments, model output and web content cannot approve actions. Persist the approved scope and its fingerprint before any effect. Repeat start requests reuse the same pending or approved record.
2. The host creates disposable worktrees from the approved SHA. A task has one canonical worktree, one current Codex thread, and at most one in-flight turn. Parallel tasks must have disjoint write scope. Dependent or overlapping work waits and gets an explicitly verified input SHA when released. A task cannot write to another task's checkout. The host must prove this separation in the worker's write sandbox before enabling coding. Until then, run read-only.
3. Start workers through the existing Codex App Server adapter with controlled working directories, workspace-scoped permissions and only required tools. Disable the goal-run MCP capabilities for managed workers to prevent recursive dispatch. Push, merge, release, CI dispatch, secrets and writes outside the approved worktrees require separate operator authority.
4. Reuse the scheduler, decision engine, managed workspace adapter, and durable reservation/reconciliation logic. The host owns the approved run and task records. Existing outbox/checkpoint modules own delivery state. Codex owns thread and turn history, and Git owns source and diffs. Store references to those facts rather than copying the entire history.

## Decision and dispatch

The planner may propose a bounded task list and dependencies once. Validate the plan against the approved goal and file scopes before creating worktrees. If the goal lacks enough detail for a safe plan, pause with one concrete question. The scheduler admits only tasks whose dependencies and write scopes have been checked.

For each task, match events by recorded `threadId` and `turnId`, and wait for a terminal turn event before reading the final answer. An answer is a claim. Check the current worktree HEAD and diff, and verify the approved checks with host-observed receipts tied to the observed code state. A worker saying “tests passed” does not create a receipt.

Use the existing decision engine first. A failing receipt yields `FIX_FAILURE`. A claimed change without proof yields `VERIFY`. A verified and still unfinished task yields `CONTINUE`. Verified acceptance yields `DONE`. Ask Codex for a bounded structured interpretation only if the answer leaves multiple plausible next steps. It can propose a next action but cannot change authorization.

A follow-up includes the fixed objective, latest verified change, one next action and the required evidence. Compare the last action and evidence fingerprint before dispatch. Three turns without new evidence stop that task with `NO_PROGRESS`. Overall `DONE` requires evidence for every acceptance criterion. The report identifies any task left incomplete.

## Recovery and control

| Condition | Host action |
|---|---|
| Ready to send | Persist a stable task and attempt ID in the outbox before calling `turn/start`. Record the returned turn ID before taking another action on the task. |
| Process restarts after acknowledgment | Resume the recorded thread and check the exact turn ID. Wait if it is active, or consume its final result once if complete. Other workspaces keep their own cursors. |
| Connection drops before acknowledgment | Set `RECONCILE_REQUIRED`. Recover only with evidence linking the reserved attempt to an exact turn. If that link is unavailable, hold for operator review. Never resend blindly. |
| Context window is full | Checkpoint the goal, verified diff/checks, current SHA, outstanding items, and next action. Compact the same thread if supported. Otherwise start a replacement and record both IDs. Wait until the previous turn is terminal before dispatching. |
| Provider rate limit or quota | Back off within the run budget for transient limits. Pause for exhausted quota. Keep the same checkpoint and preserve the run's deadline. |
| Pause or stop | Pause stops new dispatch and lets in-flight work reach a checkpoint. Stop revokes future dispatch and requests interruption. Preserve worktrees and the report. After a host restart, reconcile pending deliveries before allowing any resume. |

The host exposes a report through MCP. During an active Codex conversation, Codex can wait for terminal status and send that report in the same chat. Closing the conversation leaves the report available under its `runId`; retrieving it does not re-run the work. The host never sends unsolicited chat messages.

## Implementation and acceptance

1. Expose the four goal capabilities through the existing discovery and invocation surface, with native scope review and durable run identity. Verify duplicate-start behavior and denial of an out-of-scope request.
2. Connect the approved run to the existing managed Codex, scheduler and evidence modules. Prove one coding task on a disposable repo produces a verified follow-up from a real diff or test receipt. Prove the worker cannot write to a sibling checkout.
3. Run five tasks with distinct expected changes. Kill and restart the transport after acknowledgment for one task and verify exact-turn recovery while the others stay separate. Run a separate lost-acknowledgment case and verify it holds instead of resending. Exercise context rollover, quota pause, and stop with a deterministic fixture where live injection is impractical.
4. Verify that `goal_run.report` shows five correctly attributed results, exact test receipts and unresolved issues, with a stable run ID after restart. Record the source SHA and what was observed in the canonical checkpoint. A successful mock is recorded as a fixture result. The coding workflow is ready only after the live Windows run passes.
